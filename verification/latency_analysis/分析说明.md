# 合并 Sobel 模块的流水与延迟分析

此次仅新增验证文件，未修改生产 RTL、工程配置或比特流。

## 假设

- 一个模块内使用九个 8 位寄存器组成 3x3 窗口。
- Shift Register 为 3 抽头、间隔 800，只在有效像素期间移位，三个抽头都用于形成窗口。
- IP 抽头直接进入九像素寄存器，中间不再增加输出寄存器。
- 像素时钟 33 MHz；一行总长 1056 时钟。
- 窗口后为三级算术寄存器：Gx/Gy，abs(Gx)+abs(Gy)，阈值/饱和输出。
- 算术流水每个像素时钟运行，有效信号同步流水，不能在消隐期间一起停住。

## 周期约定与结果

以某中心像素在 SDRAM 读 FIFO 读时钟上升沿被采样的时刻 C 为起点：

- 对应窗口写入九像素寄存器：C + 2*1056 + 1 = C + 2113。
- Gx/Gy 写入：C + 2114。
- 幅值写入：C + 2115。
- 阈值/饱和后的结果写入：C + 2116。
- 若结果之后再接一个显示输出寄存级：C + 2117。

2113 已包含抽头与窗口寄存器的配合，不能再重复加一个窗口级。以上数字是相对于中心像素采样时刻的时钟间隔，不能未经统一采样边沿便等同为现有 video_hs/video_vs/video_de 的移位寄存器级数。

## 验证范围

使用本机 Quartus 13 altera_mf.v 中未改动的 altshift_taps 模型（提取单模块保存），以时钟序号作为像素标签，验证多行有效像素和行间消隐情况下的中心标签传播，ModelSim 日志见 simulation.log。标签宽度 32 位用于验证延迟，实际图像数据宽度仍为 8 位。

这是窗口与流水位置的时序分析，不是完整 Sobel 算术、整帧边界或 TFT 输出功能验证。实施时仍需验证帧切换、上下左右黑边、实际 IP 生成封装、同步信号采样约定、外部输出寄存器，以及 Quartus 时序。

## 低延迟方案：两抽头加当前行

新增 tb_latency_two_taps.sv 和 simulation_two_taps.log，不修改生产 RTL。IP 改为两个抽头，分别提供两行历史数据；当前灰度输入直接进入窗口第三行寄存器。IP 抽头与当前行在同一上升沿采样进入九像素窗口寄存器。

按相同边沿约定：中心像素采样到窗口寄存为 1057 个时钟间隔；加三级算术流水，最终结果为 1060 个时钟间隔；再接一级显示寄存则为 1061。ModelSim 标签测试覆盖行间消隐，通过 5586 个内部像素检查。相对三历史行抽头方案减少 1056 个时钟，约 32 微秒（33 MHz）。

计算公式为 1*1056+1+3=1060；若算术压缩为两级或一级，按相同结构分别为 1059 或 1058，需实际实现后的功能仿真与布局布线时序验证。只用组合计算并直接驱动 TFT 引脚不能保证接口时序，不作为优先实施方案。

实时按光栅顺序读像素时，要计算以某像素为中心的精确3x3结果，必须等下一行右侧邻居到达，因此一行加一列是该流式结构的前视需求。提高主时钟无法消除外部像素到达的等待；改变读取调度、预取或采用因果窗口需要另行设计，不能直接套用上述延迟数值。
